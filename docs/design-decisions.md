# 设计取舍：约束优先于“配置更多”

## 1. 增量维护，不重建整套系统

**约束**：现有入口、订阅身份、证书与客户端都有人在用。

选择先检查实际配置，再对指定字段做有界修改。规则变换应能说明“新增了哪些规则、哪些字段完全没变”。
代价是需要保留一些历史结构；收益是变更范围较小，回退更明确。
本仓库保留参考代码，而非承诺任意环境的一键部署。

## 2. 路由顺序也是接口契约

同一条规则在 UDP 拒绝之前和之后，实际效果可能不同。
维护函数因此对前置条件、幂等性和原规则顺序做检查，而不是简单向配置末尾追加字符串。
单元测试仅证明字符串/配置变换契约，不是对 Mihomo 全部匹配语义的重新实现。

## 3. 精确例外，不全局放开 UDP

当应用需要局部连通时，优先按进程、路径和必要端口缩小范围。
“全部 UDP DIRECT”虽然配置简单，却扩大流量范围，可能与隐私、流量和服务能力约束冲突。
测试覆盖未知 UDP 拒绝的保留以及不新增全局 STUN 端口例外。

## 4. 观测元数据，不读取业务内容

连接、握手、错误、方向和流量计数通常已能帮助定位入口/出口问题。
不需要因此收集 Cookie、Authorization 或文件内容。
元数据也有隐私风险，所以公开代码不代表公开实际采集数据。

## 5. 对照链路优先于“试着重启”

客户端访问入口、HTTP fallback、代理鉴权、出口探测和实际业务是不同层。
保留短小的对照测试，可以减少将 TLS、DNS、代理端口和业务重试混为一谈的风险。
没有关联证据时记录未定位，不用“重启后好了”替代根因分析。

## 6. 迁移保留旧入口，统计从新起点开始

文件与权限正确不代表客户端已经换入新地址。
因此把服务配置、证书、在线回读、客户端切换与实际设备验收分开；旧环境保留为回退。
历史审计库另外归档，不把旧计数直接混成新机的连续精确流量。

## 7. 一个 TUN，职责明确

需要组合本机代理时，保持单一 TUN 接管；第二个工具只提供 loopback 纯代理。
额外代理本身还需避免被上层代理再次转发，否则可能形成嵌套链路。
这仍需实际出口和文件传输证据，本仓库不将尚未验收的本机扩展宣称为已完成。
