# 三个可讨论的工程案例

这些是对既有维护过程的脱敏整理，不包含完整用户日志、真实地址或业务数据。
面试讨论重点是证据与排查边界，不是展示可以使用的代理服务。

## 案例一：局部应用连通与全局 UDP 拒绝冲突

**问题**：一套面向 TCP 服务的日常配置，不能靠全局开放 UDP 去解决个别应用的连接需求。

**处理方式**：保留进程/路径与窄范围端口例外，把规则放到最终 UDP 拒绝前；其余节点、DNS、代理组保持不变。
维护函数先检查基线，重复执行不重复新增，无法保证范围时拒绝修改。

**公开验证**：`tests/test_policy_updates.py` 对归档维护函数验证增量范围、顺序、幂等性和错误输入。

**限制**：单元测试不证明多人游戏成功，也不证明 NAT 类型和用户设备状态。
这正是将配置正确与设备可用分开描述的原因。

## 案例二：入口可达，不代表业务链路可用

**问题**：TCP 443 探测成功、HTTPS 首页返回 404、代理测速超时和应用连接拒绝，可能同时出现。
仅凭其中一个现象不能确定根因是服务端、出口还是本地代理。

**证据拆分**：

1. TCP 成功仅证明该次三次握手；fallback 的 404 不代表代理身份已鉴权。
2. 本机代理端口、规则匹配与完整代理请求需要单独验证。
3. 比较普通出口与指定出口，并检查与客户端时间窗口相关的连接元数据。
4. 应用重试、WebSocket 握手与后续持续传输分开记录。

**公开产物**：连接采集、健康探测与审计代码；仓库不附原始日志。

**限制**：不把 `10061`、EOF 或 TLS 超时统一归因给某一跳；没有逐次关联证据，就不发布“已证明根因”。

## 案例三：迁移不是替换一个 IP

**问题**：入口、身份、证书、包装服务、订阅、监控、文件权限和历史统计都要保持一致。

**处理方式**：从实际来源制作私有快照；目标机候选检查后再安装；分阶段核对依赖、权限、证书与服务。
用回读和独立链路检查补充文件校验，旧机保留回退，客户端切换单独协调。

**公开产物**：`reference/migration/` 中的阶段化流程与检查代码；所有地址和凭据已替换。

**限制**：历史迁移材料不能当作当前服务器的实时验收；脱敏仓库也不能恢复原有生产身份。

## 不放进“项目成果”的内容

没有生产吞吐基准、持续可用率或完整真实设备验收时，不编造对应数值。
本仓库的自动化检查、离线测试、历史材料和业务实测分别标注，不相互替代。

## 本次展示整理中新发现的缺陷：YAML 列表缩进

新增离线测试时发现，历史微信规则函数固定插入两空格的列表项，
但 PyYAML 默认可能输出不缩进的合法列表；混合两种缩进后，结果无法解析。

公开副本现在根据已有列表项推断缩进，再插入缺失规则；原规则和后续字段的文本不需要整体重写。
回归测试同时覆盖无缩进、带缩进、重复执行及 rules 后仍有其它字段的情况。

这个修复只在展示仓库中执行，**没有同步到生产脚本，也没有触发任何订阅更新**。
它说明离线测试能发现真实的格式兼容缺陷，但不能据此推断所有生产输入都有故障。
