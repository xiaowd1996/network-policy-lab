## 这个项目解决什么问题

一个持续维护的网络服务，不只是“配置能启动”：规则顺序会影响实际出口，客户端表现不能直接定位故障，迁移又不能随意中断旧服务。
本项目展示围绕这些约束形成的工程做法，而不是重新实现代理协议。

| 问题 | 实现方式 | 可审阅证据 |
|---|---|---|
| 增加应用例外时可能破坏原有策略 | 有界规则变换、顺序保留、幂等处理、未知 UDP 仍拒绝 | [规则维护代码](reference/maintenance/)与[单元测试](tests/test_policy_updates.py) |
| 节点测速、业务访问和链路健康混为一谈 | 分层检查入口、握手、出口与业务；采集连接元数据 | [诊断代码](reference/server/usr/local/lib/proxy-diagnostic/)与[案例](docs/case-studies.md) |
| 迁移时配置、身份和统计容易丢失 | 来源核验、候选检查、原子安装、旧机回退、历史库隔离 | [迁移参考](reference/migration/)与[操作边界](docs/operations.md) |
| 展示代码可能暴露生产环境 | 文本白名单导出、凭据占位、提交历史审核 | [安全策略](SECURITY.md)与[静态检查](scripts/validate.py) |

## 快速体验：无需服务器

使用 Python 3.12 或兼容环境，在独立虚拟环境中安装依赖后运行：

```console
python -m pip install -r requirements.txt
python scripts/validate.py
python -m unittest discover -s tests -v
python demo/policy_demo.py
```

演示会在内存中构造一份虚拟配置，调用实际规则维护函数，检查：

- 新增规则位于兜底规则之前，原规则相对顺序不变。
- 节点、DNS、代理组等非目标字段不变。
- 重复执行不产生重复规则，缺少安全前提时拒绝修改。
- 不连接服务器、不发起代理请求、不写生产配置、不启动服务。

这些结果不是客户端联网测试，也不是对实际出口的模拟判定。[完整验证说明](docs/validation.md)

## 系统结构

```text
客户端规则
├─ 局域网、国内及指定应用 ───────────→ 客户端本机 DIRECT
└─ 需代理的连接 → 独立认证入口 → 香港服务端
                               ├─ HK / 普通 AUTO → 香港直出
                               └─ 指定策略 / XO  → 住宅 SOCKS 出口

旁路能力：本机订阅 fallback、独立诊断身份、连接元数据、流量审计、可选中转
变更流程：只读检查 → 备份 → 候选验证 → 原子更新 → 回读 → 回退准备
```

“路由策略”与“传输包装”是两个维度；包装配置不能被解释为全流量强制 XO。
服务端 `direct` 是香港服务器直出，不是客户端本机 DIRECT。详见[架构说明](docs/architecture.md)。

## 工作边界与技术来源

本项目的工作集中于既有系统的配置治理、规则维护、诊断、审计、迁移与验证流程；
**sing-box、Mihomo、Nginx 及客户端不是本人从零开发的组件**。

本仓库不是生产备份，也不是一键安装器。`reference/` 中的服务与迁移脚本保留真实工程结构，可能包含写配置、权限或启动服务的操作，**仅供审阅，不应直接运行**。
